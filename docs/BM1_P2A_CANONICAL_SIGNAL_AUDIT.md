# P2-A — Canonical signal matrix and end-to-end audit

Audit date: 2026-10-08. Source/deployed baseline: b208de6661347957d5ca0bec6a6e5a6327ac79f4. This is an audit and proposed implementation sequence only. No P2 runtime code, schema, historical data, payment configuration or dashboard was changed.

## Measurement contract

Activity → Raw Signal → Normalization → Factual Aggregation → Evidence Evaluation → Intelligence → Presentation.

An activity is not automatically a valid signal. A stored label is not proof of its verification level. Historical action counts differ from operational current state. A browser identifier is not a unique person. Ticket clicks are outbound actions, not sales. Presence is bounded evidence, not universal attendance proof. Featured purchases/eligibility do not establish exposure or engagement.

The locked progression is FACT → INDICATOR → COMPARISON → INFERENCE → RECOMMENDATION. Free posting, immediate approved public pages, 14 free Discovery days, eligible extensions up to 60 days, optional Featured attention, venue identity/management separation and free guest-capable Pulse Core remain unchanged. Discovery AI's unpaid account is an expected limitation, not a reason to alter these rules.

## Canonical availability states

| State | Meaning | Required presentation |
| --- | --- | --- |
| zero observed | A relevant collector and query/window are known healthy; the query observed zero eligible records. | Show 0 with period, coverage and definition. This does not prove no real-world activity. |
| no observations | No eligible evidence records are available; collection health or opportunity may be unknown. | Show No observations; avoid demand/attendance inference. |
| not instrumented | No actual collector exists for this activity/path. | Show Not instrumented; never fabricate a numeric zero. |
| not applicable | The activity/metric cannot apply to this entity/path/window. | Show Not applicable with reason. |
| insufficient evidence | Evidence exists but fails quality, coverage, sample, identity or comparison requirements. | Facts may be shown; withhold stronger interpretation/recommendations. |

Collector errors, partial query results and disabled integrations must be explicit availability/coverage metadata, not silently converted into any of these factual states. Current event Mission Control collapses RPC failure/missing rows to zero; that behavior needs correction.

## Matrix conventions

All 28 registered signal identifiers are listed below, including identifiers without an emitter. Additional operational evidence and missing activities are explicitly labeled; no new identifier is presented as already collected.

S = public.signals through lib/signals/server.ts → record_hypeknight_signal. B = anonymous or authenticated browser; actor_id is DB auth.uid(), browser continuity is localStorage hk_anon_session_v1. U = authenticated user. P = opaque Presence participant, optionally linked to an account; neither account nor email is mandatory for event QR Presence. O = organizer owns the canonical event. Signals use server occurred_at, default confidence 1, no request/action idempotency key; their only unique index is the generated row ID. Repeated submissions/navigation can append repeated signals. Operational uniqueness is separate and listed where relevant.

E = canonical event UUID; V = venue UUID. Canonical foreign keys validate existence, not a genuine activity/context association. External events generally lack event_id and use subject_id/metadata. City/state strings are sometimes normalized by the view/search bridge, not consistently across collectors. Live signal RPC has no market_id argument and signals has no non-internal trigger; market coverage is incomplete. Attribution source below describes emitter/provider, not acquisition attribution.

Consumers: EV = owned-event summary/Mission Control and admin experimental event lab when event_id exists; MK = admin market intelligence through registered-market/entity resolution and market_daily_metrics_v1; AD = legacy admin analytics; OP = operational UI/readers. All S rows can appear in admin signal mix; no universal Intelligence interpretation is authorized by a row alone.

## End-to-end implementation trace

1. Browser view effects POST the supplied page/entity/referrer payload. The analytics API derives user_id from the session, inserts legacy event_view_logs, then attempts normalized S. Browsers can also directly call public record_hypeknight_signal. The RPC binds actor_id to auth.uid(), validates enumerations, truncates strings and clamps confidence; it does not verify activity, participant evidence, subject/event coherence, source or verification authority. /api/signals accepts any registered type, including operational and verified labels. Browser requests can claim a Pulse check-in or verified confidence without actually participating. Treat this as untrusted telemetry until trust lanes are implemented.
2. Server actions generally write the operational table then append S best effort. Failure is logged, not returned; the signal route can return ok:true despite a failed RPC. No outbox or common operation ID reconciles divergence. The feature remains usable, but measurement coverage is unknown without a failure ledger.
3. S retains raw historical observations. Normalization currently covers names, actor identity, some lengths/state values; event/venue/provider/market/participant relationships and acquisition are incomplete. Signals is not an immutable archive across entity deletion: canonical FKs use cascade; account deletion sets actor_id null.
4. Event summary RPC groups lifetime event_id/type and recognized actor/browser strings. It omits participant_id metadata, excludes external-only subjects and unidentified actors, does not dedup logical actions or filter trust/test evidence. Mission Control displays historical actions (correctly disclaimed) but calls recognized identifiers Unique Reach and falls back to zeros on errors.
5. Market JS aggregation resolves existing market_id, city/state or current attached entity geography. It can group more rows than the DB daily view, which requires stored market_id. Current RPC does not fill that column and no signal trigger exists. Entity geography resolution can reinterpret history if geography changes; it must never conflate successor businesses at one address.
6. Market averageResultsPerSearch7d adds known result counts but divides by all search rows, including missing result_count. Missing values implicitly depress the average. Peak hours use server-local getHours, not market timezone. Raw and participant-day thresholds are heuristics; coverage/bot/internal/test/trust are not evaluated.
7. Admin Lab pulls up to 20,000 raw rows for 28 days and 5,000 legacy searches, without pagination/completeness markers; backend API row caps may further constrain results. Daily aggregate rows likewise need complete-window verification. The experimental 0–100 event index uses hand-set weights/decay and volume/identified-actor confidence. It is admin-only and labeled a test bench; preserve that boundary and do not promote it to a universal Hype Score. Admin analytics city labels On fire/Busy/etc derive from arbitrary raw view thresholds, not attendance evidence.
8. Venue Factual Analytics accurately labels database-visible record counts and disclaims unique guests/verified attendance. Presence management labels status=active rows Active Check-ins without expires_at filtering; the expired April row observed during smoke testing proves stale presentation. Venue Intelligence remains deliberately unavailable.
